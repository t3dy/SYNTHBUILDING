nes-music-lab (NESMusicLab)

STABLE  C:\Dev\NESMusicLab · Python (trace conversion, MIDI export scripts)

nes-music-lab holds research-grade extraction and reconstruction code focused on Castlevania trace analysis and MIDI export, adjacent to but distinct from NSFRIPPER's own Castlevania work. It has a .gitignore in place but is not confirmed to have meaningful commit history, and is flagged as stalled -- real code exists, but it isn't clear whether it represents superseded early work later folded into NSFRIPPER, or a parallel line worth reconciling separately.

`CASTLEVANIAANALYSIS.md` documents a specific, real capture: a Mesen 2.1.1 Lua-scripted trace, 91.9 seconds long (roughly 5,524 NTSC frames), with the game's own music-engine tick rate measured at once every 7 frames (about 116.5 milliseconds, or roughly 8.6 Hz), and the song's full loop length measured at 256 engine ticks (1,792 frames, 29.8 seconds). Per channel within that loop: Pulse 1 carries the lead melody with 240 period changes and 18 distinct pitches spanning F2 to A4; Pulse 2 carries a countermelody with 289 period changes and the widest pitch range of the four channels, 23 distinct pitches from D3 to D5; the Triangle channel has 128 period changes across 9 pitches from A2 to C4; and the Noise channel fires roughly 469 hits per loop, all using a single hardware period index. The document also includes a full 79-note transcribed melody sequence and a period-to-note-to-cents-off lookup table, which is real, usable extraction data, not a placeholder or a stated intention.

The codebase backing this analysis is organized into a small formal package rather than loose scripts: `convert_trace.py` and `export_castlevania_midi.py` sit at the repository root, with a proper `src/nesml/` package underneath holding `dynamic_analysis/trace_ingest.py`, `dynamic_analysis/trace_convert.py`, `dynamic_analysis/state_trace_ingest.py`, and `export/midi_export.py` plus `export/reaper_export.py` -- alongside two top-level compatibility shims (`src/nesml/trace_convert.py` and `src/nesml/trace_ingest.py`) that duplicate the newer package-internal versions, a small piece of technical debt worth resolving whenever this project is next picked up. No document in either this project or NSFRIPPER's own files was found explicitly cross-referencing the other's Castlevania work, which means the relationship between the two remains genuinely unclear rather than settled one way or the other: this could be superseded early work later folded into NSFRIPPER's own Castlevania extraction, a parallel and non-overlapping analysis using a different evidentiary framework (the project's own docs describe a six-phase "evidence hierarchy and provenance" methodology, of which this Castlevania work represents Phase 1), or simply an independent research thread that never got reconciled with the sibling project. That ambiguity, not a lack of real content, is what actually keeps this project in "stalled, needs a decision" status rather than "safe to archive" or "safe to continue."

Neither project's docs mention the other by name in either direction, which is itself informative: if this were simply superseded early work later folded into NSFRIPPER, one would expect NSFRIPPER's own Castlevania documentation to credit or reference it, and it does not. The more likely reading, given the "evidence hierarchy and provenance" methodology this project's own docs describe as a planned six-phase framework (of which the Castlevania trace-and-transcription work above represents only Phase 1), is that nes-music-lab was conceived as a more rigorously evidenced, source-critical companion to NSFRIPPER's faster production pipeline -- prioritizing traceable provenance for each transcribed note over NSFRIPPER's broader per-game coverage -- rather than a competing or redundant effort. Whether that framing is accurate would require reading the later, unbuilt phases of its own methodology document, which describe intentions rather than completed work, so it remains an informed reading rather than a confirmed one.
