NSFRIPPER (NES Music Extraction Studio)

ACTIVE  C:\Dev\NSFRIPPER · Python (py65 6502 emulator, numpy, mido), REAPER JSFX, SQLite oracle DB, static site generator

▶ live site

NSFRIPPER builds a full NES-audio pipeline: NSF files run through 6502 CPU emulation (py65), capturing per-frame APU register state at 60Hz, which becomes 4-channel MIDI with CC11 (volume) and CC12 (duty-cycle) automation preserving the original driver's envelope, then REAPER .rpp projects using a custom unified JSFX synth called ReapNES Studio. For flagship games (Castlevania 1, Contra, Wizards & Warriors) it goes further, parsing the actual ROM sound-driver code and validating output frame-by-frame against Mesen-emulator hardware traces -- the project's fidelity hierarchy (Trace > SysEx > NSF emulation > CC automation > ADSR approximation) is a load-bearing rule repeated throughout its 40-rule architecture doc.

A SQLite-backed 'oracle' knowledge base (ANTIRIPPER/antiripper_v2.db) records extraction decisions, prevention patterns, and hardware facts as institutional memory across sessions -- a genuinely mature piece of infrastructure among Ted's projects. The site is live and generated deterministically from output/.

The last commit (2026-04-20) shipped a three-variant architecture specifically so Ted could ear-test and choose: Variant A 'Double Dose' (audio stems + JSFX), Variant B 'Live Wire' (pure JSFX/MIDI, playable live), and Variant C 'Ditto Head' (JSFX-rendered stems, deferred, never built). The README's own roadmap says the next step is simply: listen to A and B, decide whether to keep the Python stems pipeline, go JSFX-only, or build C. That decision was never made and never logged -- no commits since.

A Bach-mashup side project (bach_nes_mashup.py and siblings) pairs J.S. Bach MIDI with NES instrument timbre presets extracted from Castlevania/Contra/Metroid/Gradius stage palettes; see CHIPPEDONBACH.md for the full account, including two finished MP4 preview videos sitting at the C:\Dev root and 117 generated-but-unrendered projects.

Open technical items at last commit: whether the Python DSP fixes (14kHz analog lowpass, DC blocker, bandlimited pulse synthesis) need porting into the live JSFX synth too; a known ~15% non-linear-mix overload from summing independently-rendered stems in REAPER's bus; Metroid's intro track hangs the py65 emulator; a Capcom 6C80 ROM parser (~2 weeks estimated, not started) that would add ~40 games to trusted status; and three unsolved hardware mysteries called out explicitly in its own docs (why Castlevania produces noise drums without the $4015 bit-3 enable the spec requires; why SMB's driver writes a constant DC value to $4011 every frame; region-driver divergence between CV3's US and JP releases).

On disk, verified directly rather than taken from the project's own claims: `output/` holds 48 game folders and 2,063 MIDI files paired 1:1 with 2,063 RPP REAPER projects. The 40-rule figure in the architecture doc is also directly countable -- `.claude/rules/architecture.md` runs Rules 1-12, 17-18, 22 and 26-40 (topping out at "40. Noise HW Envelope Must Be Simulated in Capture"), with the remaining rules 13-16, 19-21 and 23-25 living in a companion `docs/ARCHITECTURE_REFERENCE.md`. The project's own driver-census claims are internally inconsistent in a small, honest way: CLAUDE.md cites both a "271-game census" (2026-04-14, and the 271 figure does sum exactly from the documented driver-family table) and a separate "298 games" register-level analysis three days later -- two different sweeps at two different dates, not a contradiction.

The three delivery variants behind the unmade ear-test decision have real architectural differences, not just naming: Variant A "Double Dose" plays 4-5 audio stems and 4 MIDI+JSFX tracks simultaneously by default, unmuted, and they are deliberately *not* sample-aligned (JSFX carries REAPER's MIDI-engine latency; the stems start exactly on bar 1), so the two can be A/B'd by muting one side at a time. Variant B "Live Wire" is pure JSFX -- 4-5 tracks running `ReapNES_APU2_v2.jsfx`, which resolves note data through a three-tier priority cascade (captured hardware SysEx replay, if present, beats CC11/12 automation, which beats plain keyboard ADSR). Variant C "Ditto Head" is, today, an unbuilt placeholder -- literally an identical copy of B's folder, standing in for a planned offline JSFX-to-WAV render pass that was never written. The project's own fidelity-gap table is candid about a real known shortfall: the audio stems carry five specific hardening rules (27, 30, 33, 34, 35) that the live JSFX synth only implements two of (27 and 34), with an explicit warning that JSFX "will sound SHARPER/BUZZIER than stems until Rule 35 ports" -- meaning the A/B ear-test Ted still needs to run isn't just a taste call, it's confirming whether that documented DSP gap is audible enough to matter.

The oracle database (`ANTIRIPPER/antiripper_v2.db`) is more structured than a simple lessons-log: seven tables (`hardware_facts`, locked and immutable; `prevention_patterns`; `driver_families`; `evidence_items`; `claims`, which agents may propose but never promote to accepted status themselves; `decision_records`; `attempts`), accessed only through a Python wrapper (`agent_oracle.py`) that enforces a preflight-attempt-outcome workflow rather than raw SQL access. Its own audit (2026-04-14) is honest about gaps: 105 of 225 "best output" games have no decision record (47%), the attempts and claims tables are empty, and 140 of 321 surveyed games remain unclassified entirely -- this is real infrastructure, used inconsistently, not a finished system.

The open wishlist (`state/wishes.json`, 20 items) contains two flagged critical and not-started alongside WISH16's Bach-render backlog: WISH01 would port CC11/CC12 automation handling into the flagship Console synth, which the project's own note says "fixes playback fidelity for all 1,099 projects at once" -- the single highest-leverage unstarted code fix in the family, distinct from the A/B/C listening decision, which is a choice rather than a fix. WISH18 flags that a large body of uncommitted Antigravity-session work (scripts, song sets, the Bach mashups, Castlevania 2/3 extractions, 36 documents, trace JSON files) sits unprotected, with its own text reading "One crash from gone." The project's `docs/ROM_MUSIC_MYSTERIES.md` documents at least two genuinely unresolved hardware puzzles beyond the noise-drum question already summarized: Super Mario Bros.'s extracted pulse periods measure almost exactly half (a ~2.003-2.005 ratio across 22 of 22 notes checked) of ground truth from Mesen traces, while the triangle channel is unaffected -- the current workaround transposes down 12 semitones without knowing why the discrepancy exists, suspected to trace to an uninitialized zero-page octave variable in the ROM's own driver code, and it remains untested whether this is SMB-specific or a wider pattern across the other traced games.
