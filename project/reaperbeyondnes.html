REAPERBEYONDNES

ACTIVE  C:\Dev\REAPERBEYONDNES · Python, REAPER, per-chip extraction tooling

REAPERBEYONDNES is a declared multi-system successor to the NES-only extraction work in NSFRIPPER and its siblings, scoped to cover GBA, SMS, Saturn, Genesis, SNES, GBC, and Virtual Boy sound chips as well. It is heavily structured for that scope: per-chip project folders, a tools/ directory, a kb/ knowledge base, and its own agent-protocol document ('THE_LITURGY.md') describing how sessions should work on it.

The most important fact about this project is not what it contains but what it lacks: it is confirmed to not be a git repository. Everything in it -- however much real extraction and tooling work has gone in -- currently exists in exactly one place, on one disk, with no version history and no remote backup. This is a materially different category of risk from every other 'stalled' project in this catalog, which at worst risks losing momentum, not losing the work itself.

The per-chip scope is concrete and directly verifiable by directory listing: ten system folders exist under `projects/` -- `gb_dmg`, `gba_directsound`, `gbc_sound`, `genesis_psg`, `genesis_ym2612`, `gg_sn76489_stereo`, `nes_apu`, `sms_sn76489`, `snes_sdsp`, and `vb_vsu` -- one fewer platform than the originally declared scope, since the project's own `memory/MEMORY.md` (dated 2026-04-23) explicitly records that Saturn support was deferred rather than dropped silently.

The honest, load-bearing finding from a direct inspection of those folders is that nothing is actually built yet in any of them: every single system's `renders/`, `tests/`, `jsfx/`, and `driver/` subdirectories contain only a placeholder `.gitkeep` file, with zero real code or audio present across all ten platforms without exception. What does exist is a first wave of research: a session referred to internally as "KB Wave 1" (2026-04-24) produced nine chip-reference documents under `kb/chips/*.md`, generated via parallel background research agents and confirmed to have all passed their own validation pass. The NES entry in that knowledge base (`kb/chips/nes_apu.md`) was not written from scratch -- it explicitly imports 19 of NSFRIPPER's 38 architecture rules directly, with the remaining 18 generalized out into project-wide protocol documents applicable across all ten target systems, which is a genuinely sensible reuse of NSFRIPPER's hard-won 2A03 knowledge rather than re-deriving NES facts a second time. A first vertical-slice implementation task, targeting the Sega Game Gear's SN76489 chip (`HANDOVER_03`), is marked "unblocked" and ready to start but had not been started as of this survey -- meaning the single most useful next action for this project is not more research but actually writing the first real chip driver against research that already exists and is sitting unused.

This changes the framing of the project's status somewhat from a pure inventory: REAPERBEYONDNES is not "heavily structured, substantial work already done and merely unprotected by git" so much as "heavily structured research and scaffolding, zero implementation, and additionally unprotected by git" -- both things can be true (the structure and the NSFRIPPER-rule reuse are real, careful work), but a reader should not infer from the elaborate per-chip folder layout that extraction code for GBA, SMS, Genesis or any other listed system actually exists yet. The `git init` and first-commit recommendation from `MUSICHACKING.md` remains correct and unchanged by this finding -- if anything it matters more, since a disk failure today would lose real prior-research documents (the nine KB chip references, the rule-reuse mapping) and not merely a head start, even though it would not lose working extraction code, because none currently exists.
