ReapNES Studio (ReapNESClod)

ARCHIVED  C:\Dev\ReapNES-Studio · REAPER JSFX, C++/JUCE + CMake (VST3, Windows/MSVC), Python tooling, NES-MDB preset corpus

ReapNES Studio set out to be a REAPER-based NES music production environment: pick a game's instrument palette, generate a ready-to-open REAPER project, play it live off a MIDI keyboard or import MIDI onto NES-timbre instruments. It shipped two parallel synth implementations -- a JSFX plugin and a JUCE-based VST3 (CMake, generated MSVC solution files, never fully wired up) -- plus a Python project generator and a 54,000+ instrument preset corpus extracted from the NES Music Database (reference/training data, not original work).

Its docs/BLOOPERS.md (14 documented blunders) and docs/SUCCESSANDFAIL.md chronicle a difficult early arc: JSFX plugins silently rejected as instruments over a missing in_pin:none declaration and a stray '//tags:' comment prefix; a Unicode character causing a silent compile failure; REAPER caching a broken compile until the file was renamed; '^' meaning POWER not XOR, breaking the LFSR noise feedback bit; and, most seriously, generated .rpp projects that could not get MIDI keyboard input routed to the JSFX instrument at all, because JSFX lacks the VST 'instrument' flag REAPER checks for live routing. A hand-built VST3-based project worked for keyboard input but couldn't be generated programmatically, because REAPER's RPP format for VST3 requires an opaque base64 plugin-state blob only REAPER itself can produce.

HANDOVER_KEYBOARD_AND_SYNTH.md documents the eventual fix strategy for the JSFX keyboard problem (diff a REAPER-saved working .rpp against a generated broken one; add a 'Keyboard Mode' toggle so the plugin ignores the MIDI channel filter for live input) plus explicit anti-patterns to avoid repeating. The final commit's message -- 'fix MIDI keyboard routing' -- indicates this was resolved before folding into NSFRIPPER, whose ReapNES_Console.jsfx inherits the working design.

NEXTPHASES.md describes an intended follow-on (Phase A: expose every NES timbre parameter as labeled knobs; Phase B: comparative timbre study; Phase C: educational website; Phase D: animated-knob YouTube pipeline; Phase E: drum tracker) with no commits recorded here -- any continuation happened inside NSFRIPPER instead, where the Bach-mashup and console synth work now live.

`docs/BLOOPERS.md` documents fourteen blunders, confirmed by direct count, each traceable to a specific root cause: a `//tags:instrument` line parsed as a comment rather than a directive (silently breaking MIDI routing); a missing `in_pin:none` declaration making REAPER treat the plugin as an effect rather than an instrument; a stray Unicode character causing a silent compile failure; REAPER's JSFX compile cache surviving even a deleted `reaper-jsfx.ini`, fixed only by renaming the file; guessed RPP tokens (`MASTER_SEND`, `REC_INPUT`) that REAPER silently ignored rather than rejected outright; a MIDI-input `REC` field that took four separate failed attempts at the right field count before the team reverse-engineered a REAPER-saved template instead of guessing further; a `SOURCE MIDIPOOL` and inline-event approach that both failed silently before `SOURCE MIDI FILE "path"` finally worked; an inaudible DC-offset mix (-0.784 silent, -0.45 while playing) that fooled the meters; `^` meaning power, not XOR, breaking the noise LFSR; every track initially playing all four APU oscillators simultaneously as an unintended wall of sound, fixed by adding a channel-mode slider; community-sourced MIDI files using inconsistent, effectively random channel numbers (one Mega Man 2 file had its "Air Man" part split across channels 1, 3 and 4), fixed with an auto-remap step; drum notes needing real decay envelopes rather than a bare on/off to avoid audible clicking; a 71-file classical-MIDI quality survey (rated Perfect/Good/OK/Bad, with only the top two tiers actually used) that turned up a "Für Elise" file whose piano part was, bizarrely, tagged as electric bass; and a hard practical limit of roughly three simultaneous voices for classical material, where Bach's two-voice inventions and the Goldberg Variations worked but full Beethoven symphonies did not.

The project's own closing self-assessment in `docs/SUCCESSANDFAIL.md` is unusually blunt for a status document: it states directly that "the user still cannot open a generated project and hear sound without manual intervention," against a scorecard of six documented successes and six documented failures -- an honest verdict, not a soft one, and part of why this project stayed archived rather than pushed toward a premature "done." The unresolved VST3/JUCE path has a named recommended fix that nobody executed: `SYNTHPROBLEM.md`'s "Option D" reads, in substance, that the user opens REAPER once, adds the VST3 manually to a track with default settings, and saves it as a template; the generator then extracts that exact block and reuses it (with modified parameters) for every future project, rated "low effort, one-time manual step, then fully automated forever" and marked as the document's own recommendation over three other options it considered and set aside (reverse-engineering the binary state blob directly, a ReaScript runtime swap between JSFX and VST3, or hunting for an undocumented REAPER preference to route keyboard MIDI into JSFX). `NEXTPHASES.md` lays out five dependent follow-on phases that were never started once the project folded into NSFRIPPER: Phase A (Synth Console Polish) would expose every hardware parameter as a labeled control; Phase B (Comparative Timbre Study) would mine the 54,000-preset corpus into structured per-game, per-channel envelope data; Phase C (an educational website extending the timbre data into per-game parameter pages) depends on B; Phase D (animated-knob playback visualization for YouTube) depends on A; and Phase E (a step-sequenced drum tracker, aimed at being more approachable than FamiTracker) depends on both A and B.

Stuck / next
The VST3/JUCE path (working keyboard input, un-scriptable RPP generation) was never resolved. SYNTHPROBLEM.md's recommended fix -- save one project manually with the VST3 loaded, extract that block as a template -- was never executed. This is the best-scoped open technical problem in the whole family.
