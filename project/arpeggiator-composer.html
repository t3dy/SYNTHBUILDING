arpeggiator-composer

STABLE  C:\Dev\arpeggiator-composer · JSFX, ReaScript, Python (core/, reascript/, reaper_projects/)

arpeggiator-composer is a REAPER-targeted deterministic MIDI arpeggiator, structured like a real small software project rather than a one-off script: a core/ logic layer, a jsfx/ folder for the REAPER-side plugin component, a reascript/ folder (REAPER's own Lua/Python API, run inside REAPER), reaper_projects/ for example projects, and a tests/ folder. Unlike the rest of this catalog it isn't NES-specific -- it's general-purpose composition tooling that happens to live in the same REAPER/JSFX ecosystem. It's flagged as stalled and uncommitted, so its actual completeness relative to its own test suite hasn't been independently verified in this survey.

The arpeggiator itself, per its own README, is a genuinely fully-specified feature set rather than a stub: six pattern shapes (up, down, up-down, down-up, as-played, and a seeded-random mode for reproducible randomness), tempo-synced note divisions from a whole note down to a 32nd, including triplets, a configurable one-to-four-octave range, step-skip patterning, a gate-length control from 10% to 200% of the available note duration, swing, legato with configurable overlap, one-to-four-voice harmony with independently configurable interval, spread and inversion settings, deterministic seeded velocity humanization (meaning the same seed reproduces the same "human" timing/velocity variation rather than being different every run), accent patterning, transposition up to two octaves in either direction, and a panic/all-notes-off control -- a feature list comparable in scope to a commercial arpeggiator plugin, not a toy script.

The project's folder structure matches that ambition: `core/` holds three design documents (`sequence_spec.md`, `state_model.md`, `transformation_rules.md`) rather than code, meaning the logic is specified but its actual implementation status relative to that spec was not independently verified in this pass; `jsfx/` holds five separate JSFX files (`arp_composer.jsfx`, `arpsynth.jsfx`, `simplearp.jsfx`, `theme_input.jsfx`, `voice_engine.jsfx`), suggesting the arpeggiator logic and a basic synth voice were built and iterated on as separate concerns; `reascript/lua/` holds three REAPER-API automation scripts (`create_test_midi_item.lua`, `insert_sequence_into_take.lua`, `sequence_debug_dump.lua`), with an empty parallel `reascript/python/` folder suggesting a Python REAPER-scripting path was planned but never started; `reaper_projects/` holds two example `.RPP` files; and `tests/` holds three specification documents describing test cases for note lifecycle, sequencing, and transformation logic, rather than an automated, runnable test suite. No document anywhere in the repository -- README, roadmap, engine notes, or a takeaways file -- states a reason for the project being stalled; the closest thing to a hard fact on this point is that the repository's own git history shows zero commits despite a `.git` folder existing, meaning the "stalled and uncommitted" status recorded elsewhere in this catalog is accurate, but genuinely undiagnosed -- nobody has gone back to ask why work stopped, which UNFINISHEDSTATUS.md already names as the one project in this family where that basic accounting has not been done.

Because the `.git` folder exists but holds no commits, the project sits in an unusual state relative to the rest of this catalog's "stalled and uncommitted" entries: REAPERBEYONDNES and nes-music-lab have no version control infrastructure configured at all, while arpeggiator-composer has the infrastructure in place and simply never used it -- a smaller, one-command fix (`git add -A && git commit`) than either of those two projects would need, and arguably an even lower-effort action item than the "run its own test suite" next step already identified, since the test suite is itself only specification documents rather than executable tests that could actually be run today. Until those specification documents (`test_note_lifecycle_cases.md`, `test_sequence_cases.md`, `test_transform_cases.md`) are turned into real, runnable tests, "run its own test suite" is not yet an available action -- the more honest immediate next step is writing the test harness the specs describe, then running it, rather than assuming a runnable suite already exists.
